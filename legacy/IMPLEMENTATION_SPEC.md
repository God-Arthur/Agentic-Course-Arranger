# 系统工作说明：从模拟需求到预置课表

## 1. 系统定位

系统不是正式教务系统，也不自动锁定课位。它是一个课程资源规划与仿真实验原型，研究 AI 能否通过主动获取信息、发现可接受替代方案并触发重新分配，改善预置方案。

## 2. 每次运行的实际流程

1. **建立校园状态**：读取课程班次、类别、时段、容量，以及学生的培养要求、年级/政策优先组和已知偏好。本 MVP 生成合成数据。
2. **形成初始需求**：每个模拟学生具有隐藏的真实效用。系统只暴露有限的初始志愿和培养要求，不把隐藏真值交给规划控制器。
3. **运行对照基线**：按照一个简化的“优先组 + 随机顺序 + 志愿顺序”机制生成第一份分配。它仅作为实验对照，并非浙大官方机制复刻。
4. **优化初始预置方案**：在已知偏好、课程容量、每名学生目标门数和时间冲突约束下，生成可行分配。安装 OR-Tools 时使用 CP-SAT。
5. **诊断协调机会**：估计初始志愿需求压力，找出热门课位未满足的学生，再从同类课程中寻找有空余容量、与学生公开兴趣有一定关联的候选替代课程。
6. **决定问谁、问什么**：规则控制器按透明启发式选择；可选 LLM 控制器只看到公开特征与候选问题，不接触隐藏真实偏好。
7. **获取信息**：合成学生模拟回答是否接受替代课，并提供带噪声的匹配度评分。实际使用时，这一步必须替换为学生本人确认。
8. **重新分配**：将学生确认接受的替代方案加入已知偏好，再求解新的配置。
9. **验证并评估**：报告容量违规、时间冲突、必修课程满足率、平均效用、低分位效用、空缺目标课位等指标。
10. **交付输出**：导出每名学生的预置课程、课程需求表、协调过程日志和实验摘要。

## 3. 规划控制器与优化器的分工

- **规划控制器（候选 AI 核心）**：选择最值得获取的信息，提出具体查询，决定是否继续协调。
- **分配优化器**：根据公开并已确认的偏好计算可行方案，不让 LLM 自行编造或修改容量。
- **验证器与评估器**：检查硬约束和计算指标，避免由 LLM 给自己打分。
- **模拟学生**：隐藏真实偏好只用于仿真答复与离线评估，不能传给规划控制器。

## 4. 重要约束与风险边界

- 真实预置方案必须是建议或待确认状态。未经授权，不应代替学生提交正式选课或提前锁定课位。
- 容量和最终课表时间冲突是硬约束，不能通过效用分数抵消。
- 真实学校优先级顺序需由授权方提供并显式配置；MVP 的优先组与比例只是示例。
- 现行选课中的“同类型可将时间冲突课程作为志愿替代项、不同类型的冲突选择限制”等细则，需要由教务规则进一步形式化。MVP 只实现最终分配不得时间冲突，并对初始偏好做了简化。
- 合成学生偏好不能代表真实学生。上线前需要匿名化数据、学生授权及真实偏好验证，并对不同群体进行公平性审查。
- 本系统应输出推荐理由与约束冲突报告，不能只输出名单。

## 4B. 部署形态（已实现，详见 [DEPLOYMENT.md](DEPLOYMENT.md)）

- 系统作为**单个 Streamlit 进程 + 本地文件状态**交付：`Dockerfile` + `compose.yaml` 构建 `python:3.12-slim`
  之上的非 root 镜像，四个命名卷承载表格、语义缓存、运行日志与已保存运行，`down`/`up` 不丢状态
  （逐字节 sha256 核过）。没有数据库、没有独立前端。
- 数据/缓存/日志/导出目录全部由环境变量决定（`runtime_paths.py`），容器里指向卷；
  界面的表格目录输入被限制在 `PLANNER_DATA_ROOT` 之内，越界被拒（`TablePathNotAllowed`）。
- 运行日志是追加式 JSONL（`runlog.py`）：开始/结束/失败与耗时，LLM 调用数与回退**分开计数**，
  写入前脱敏，写入失败不打断业务。已保存运行（`run_store.py`）同名即拒绝覆盖。
- 机器验收：`deployment_acceptance.py` 九项（无密钥全流程、硬约束独立复核、坏表格拒绝、路径越界、
  LLM 失败留痕回退、日志可运维、拒绝静默覆盖、依赖钉死、导出可读回），可在镜像内实跑；
  `--stage save/verify/clean` 三个子命令用于"重启后状态还在"的核对。
- 这一层的行为由 `tests/test_deployment.py`（25 例）看守，与研究判据零交集。

## 5. 建议的下一阶段

1. 将 `generate_world()` 替换为从真实课程/培养方案 CSV 读取数据的适配层。
2. 定义统一的 `CourseSection`、`StudentProfile`、`PolicyRule` 数据契约。
3. 严格实现学校第一轮志愿规则、第二轮规则、政策优先级与彩票/随机过程，形成可复现的现行机制基线。
4. 让学生通过明确同意的界面确认预置课表，且保留撤回/修改能力。
5. 用历史数据回放和盲测比较现行制度、规则式协调、LLM 主动协调；同时控制询问次数，确认 AI 的收益不是单纯来自额外信息。
6. 在任何真实分配前，做容量、冲突、必修满足和优先级遵循的自动化验收测试。

## 6. 接入真实数据前的数据契约（建议）

### 课程班次 `courses.csv`

建议字段：

- `course_id`：唯一课程班次 ID，而不是只有课程名称。
- `course_name`：课程名称。
- `category`：教务定义的课程类型。
- `time_slot`：用于检测冲突的标准时段 ID；若实际课程跨多个时段，应扩展为时段集合。
- `capacity`：核准容量。
- `topics`：课程内容标签或课程描述。
- `prerequisites`：先修条件。
- `eligible_programs` / `eligible_years`：选课资格（如适用）。

### 学生档案 `students.csv` 与 `.skill`

建议字段：

- `student_id`：去标识化学号或项目内部 ID。
- `year`：年级。
- `priority_group`：经教务授权确认的制度优先组；必须单独定义正式排序，不根据自然语言推测。
- `completed_course_ids`：已经修读并通过的课程。
- `required_course_ids`：培养方案要求本学期优先考虑的课程。
- `skill_path` 或对应的 `.skill` 文本：学生自愿提供的兴趣、学习目标、偏好及限制。

真实 `.skill` 应先解析为带来源和置信度的偏好信息。模型推断与学生明确陈述必须分开存储。涉及时间不可用、必修要求、资格限制的字段应由学生确认或由教务数据提供，不能仅依赖 LLM 猜测。

### 正式预置方案 `preassignments.csv`

至少包含：`student_id`、`course_id`、`reason_code`、`source_of_preference`、`policy_version`、`status`（例如 `proposed` / `confirmed`）。默认状态应为 `proposed`，只有经过确认及授权流程后才可转换为正式占位或选课记录。

### 验收不变量

- 每个课程班次的分配人数不超过容量。
- 同一学生的最终课表不存在禁止的时段冲突。
- 资格和先修条件成立。
- 优先级处理符合明确版本的制度规则。
- 每条建议都可追溯其培养要求、初始偏好或已确认的替代选择来源。
- 规划前后都保存指标、数据版本、模型/控制器版本和操作日志。

## 7. AI 语义需求建模模块（已实现并已判完，两个处理）

上面 §2 的十步描述的是"协调提案"这个 AI 位点。本节描述第二个位点：把学生 `.skill` 解析成需求模型，让解析结果**直接进入预置优化目标**，再经完整两轮选课模拟评价最终结果。该位点的实测结论是阴性（两个处理的主判据都未过预注册门槛），数字只写在判定文件与 README §7B / §7C 里，由脚本搬运，本文件不复制第二份。

- **输入**：学生 `.skill` 原文、官方课程描述与教学目标、培养要求。**输出**：可追溯的学习目标（逐字引句＋重述）、逐课相关度、学生明确点名的课程、其表示可接受的替代项、三态需求类别（明确要求 / 一般偏好 / 仍有歧义）、不确定性与原文证据。代码：第一处理 `semantic_needs.py`（臂 I/J/K，只补相关度），第二处理 `semantic_needs_v2.py`（臂 I2/J2/K2，补全上述字段）。两个处理各自预注册、各自出判定，不合并成一句"AI 有用/没用"。
- **硬约束归规则**：必修清单、容量、时段互斥、先修资格、每人课位数一律由 `institution.hard_requirements()` 与优化器决定。模型即使违反指令自己上交一份 `hard_requirements`，写回时也以规则输出覆盖；`tests/test_semantic_needs_v2.py::HardConstraintsStayOnTheRuleSide` 与 `results_need_v2/_selftest_hard_constraint_pin.py`（内存里改源码副本再 exec 的变异机）共同证明这条越权会被拦。**这份丢弃目前是静默的**，`problems` 里不留"模型试图改动必修"的记录，故本项属"已验证的边界"而非"已交付的可观测能力"，README §9 记为已知未证。
- **隐藏真值不进模型**：`true_scores` 只用于仿真答复与离线评估。`tests/prompt_isolation.py` 对两条需求解析臂同时做正反两侧核对（正向要求每生原文逐字恰好一次出现、课程清单非空、字段集等于公开契约；反向先把每名学生的效用换成全局唯一哨兵数字，再断言字段名、整张效用表、哨兵数字与 API key 都不出现在实际发出的正文里）。只有反向那半的核对会对空载荷也通过，所以正向半是它不空转的前提。
- **成本与可复现**：档案级写穿缓存 `semantic_cache/`，键含解析器版本（`semantic-need-v1` / `semantic-need-v2`），改提示词或字段必须升版本号——升版会让已落盘分块被 `analyze_need_v2.py` 的配置一致性检查拒绝合并；结构化输出校验失败即标记回退，不静默改数据；批次按分块串行，每块跑完立即落盘。
- **验收**：判定只能由 `analyze_semantic_need.py` / `analyze_need_v2.py` 从 `raw_rows.csv` 算出（种子不全、配置漂移、机制集合不符、被引用的列缺失一律不出稿），README 侧由 `verdict_readme_guard.py`、`need_v2_number_guard.py`、`prereg_coverage_guard.py` 等逐行核对；交付前 `results_need_v2/_run_delivery_guards.sh` 重跑全部能失败的核对与全套离线单测。
